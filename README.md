# ETF Intelligence Platform — Phase 1 + 2 + 3 + 4

A Bloomberg-style research workstation for NSE ETF swing trading.
**Phase 1**: data pipeline, indicator engine, relative strength, ranking,
Market Overview + ETF Detail. **Phase 2**: RRG engine, non-repainting
Renko, formal Explainability Engine, Opportunity Scanner. **Phase 3**: a
no-code Strategy Builder and a walk-forward backtester. **Phase 4**: an
opt-in GitHub Action for daily NSE data fetch, in-page notifications, and
an AI Research Assistant (bring-your-own API key).

## Stack

React + TypeScript + Vite + Tailwind v4 + Zustand + TanStack Table +
TradingView Lightweight Charts + Plotly (basic build, lazy-loaded). Pure
static site — no backend, no server.

## Getting started

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # type-checks then builds to dist/
```

## Refreshing data

Data comes from a normalized JSON snapshot in `public/data/`, generated by
`scripts/excel_to_json.py` from your master Excel workbook (one sheet per
symbol, NSE bhavcopy-style columns).

```bash
python scripts/excel_to_json.py path/to/your.xlsx public/data
```

This is a manual step by design (no scheduled fetch yet) — run it, commit
the updated `public/data/`, push. The app will pick up whatever symbols are
in `public/data/manifest.json`; there's no hardcoded symbol list anywhere in
the frontend, so adding or removing an ETF is just adding or removing a
sheet in the source workbook.

## Deploying to GitHub Pages

```bash
npm run build
```

Then either:
- Commit `dist/` to a `gh-pages` branch (or to `/docs` on `main`) and point
  the repo's Pages setting at it, or
- Add a small GitHub Action that runs the build and publishes `dist/` on
  every push to `main` (e.g. `peaceiris/actions-gh-pages`). This is a
  build-only CI step — it doesn't touch NSE or fetch new data, so it's
  independent of the manual data-refresh workflow above.

Routing uses `HashRouter` (URLs look like `#/etf/NIFTYBEES`) specifically so
GitHub Pages — which can't rewrite arbitrary paths to `index.html` — serves
ETF detail pages correctly on a hard refresh or direct link.

## Phase 4: automation & AI

**Daily NSE fetch ships disabled.** `.github/workflows/daily-data-fetch.yml`
exists and can be run manually right now (Actions tab → "Daily NSE Data
Fetch" → Run workflow) — but its `schedule:` trigger is commented out. Read
the comments at the top of that file before enabling it; NSE is known to
rate-limit/block automated and datacenter-IP traffic (GitHub-hosted runners
are datacenter IPs), and this needs a real test run before you trust it.

`scripts/fetch_nse_daily.py` tries two sources in order:
1. **`nselib`** (primary) — includes delivery data, but was written by
   reading its source rather than running it against live NSE (my sandbox's
   network egress doesn't reach nseindia.com).
2. **charting.nseindia.com** (fallback, OHLCV only, no delivery data) — this
   one I could actually verify live, via a tool able to reach it from
   outside that sandbox. Confirmed real: the response shape, and that it
   returns plausible live data for both an index and an ETF. Also found and
   fixed a real discrepancy this way — a "known scripcode" cache table for
   this API claimed token 8080 was NIFTYBEES-EQ, but a live request using
   that exact token returned silver-ETF-range prices (~220-250), not
   Nifty-range (~270). So this script never trusts a cached token; it
   always resolves symbols dynamically.

Separately, testing against an actually-blocked endpoint (this sandbox's
own network restrictions gave me that for free) surfaced a real bug:
`nselib`'s wrapper pre-fills its output with the right columns *before*
fetching, so a blocked request can come back looking like "valid response,
zero rows" instead of an error — indistinguishable from a normal
non-trading day unless you check for it. The script has a batch-level
sanity check for exactly this (zero new rows across *every* symbol on a
weekday is treated as a failure, not "no news today").

**Bottom line: run it manually and read the Action's summary output before
trusting the schedule, for either data source.**

**Notifications** are "today's notable events," not "new since you last
checked" — there's no persistence to know when you last checked. Fresh
Renko reversals, recent RRG quadrant transitions, volume spikes/expansion,
and today's BUY-rated ETFs surface in the bell icon in the header
(`src/lib/notifications.ts` + `NotificationsPanel.tsx`), computed from data
already on the page — no new fetches.

**AI Research Assistant** (`/assistant`) is a bring-your-own-key chat
interface wired to the real Claude API, called directly from the browser
using Anthropic's `anthropic-dangerous-direct-browser-access` header (the
documented pattern for exactly this "no backend, user supplies their own
key" case). The key lives only in memory for the session (zustand store
with no persist middleware) — never committed, never saved, gone on
refresh, consistent with the no-storage decision from Phase 1. Every
question is grounded in the platform's own current rankings/explainability
output (`src/lib/assistant/buildContext.ts`), not the model's general
knowledge about these ETFs, and re-grounded on every turn so a long
conversation can't drift onto stale numbers.

## Architecture

```
public/data/manifest.json, symbols/*.json     <- generated by excel_to_json.py
        |
src/lib/dataProvider.ts                       <- DataProvider interface; only this
        |                                        file knows where data comes from
src/lib/indicators/*.ts                       <- pure functions: EMA/ATR, volume,
        |                                        delivery, trend, relative strength,
        |                                        RRG (rrg.ts), Renko (renko.ts) --
        |                                        every one of these is vectorized
        |                                        (full per-day arrays), not just
        |                                        "today"
src/lib/indicatorTimeSeries.ts                <- the single source of truth: wires
        |                                        all indicators into one array-per-
        |                                        field SymbolTimeSeries, plus
        |                                        snapshotAt(ts, i) to read any day
src/lib/computeIndicators.ts                  <- live dashboard = snapshotAt(ts,
        |                                        lastIndex) -- thin wrapper, see
        |                                        "No-lookahead guarantee" below
src/lib/ranking/compositeRanking.ts           <- weights indicators into a 0-100
        |                                        score + an explainable breakdown
        |                                        (used both live and per backtest day)
src/lib/explainability/explain.ts             <- formal Explainability Engine:
        |                                        Signal / Confidence / ✓✗ checklist
src/lib/backtest/fields.ts                    <- field registry for the no-code
        |                                        Strategy Builder (type + accessor
        |                                        per selectable field)
src/lib/backtest/runBacktest.ts               <- walk-forward backtest engine
        |
src/lib/notifications.ts                      <- derives today's notable events
        |                                        from already-computed data
src/lib/assistant/buildContext.ts             <- grounds the AI assistant in this
        |                                        platform's own current data
src/lib/assistant/claudeClient.ts             <- browser-direct Claude API client
        |                                        (BYOK, no backend)
        |
src/store/useMarketStore.ts                   <- zustand store: loads data, holds
        |                                        benchmark/weights, recomputes,
        |                                        also holds full RRG/Renko series
src/store/useAssistantStore.ts                <- in-memory-only API key + chat
        |                                        history (no persist middleware)
src/pages/, src/components/                   <- Market Overview, RRG Analysis,
        |                                        Scanner, Strategy Builder,
        |                                        Assistant, ETF Detail
        |
scripts/fetch_nse_daily.py                    <- daily fetch script run by the
.github/workflows/daily-data-fetch.yml            (disabled-by-default) GH Action
```

**Swapping the data source later** (a live NSE API, a backend, etc.) means
writing one new class that implements `DataProvider` in
`src/lib/dataProvider.ts` — nothing else in the app changes.

## No-lookahead guarantee (why the backtester can be trusted)

Every indicator in `src/lib/indicators/*.ts` is vectorized to produce one
value **per bar**, using only that bar and earlier ones — never a value
computed from the full series and then "read off the end." This is what
makes `src/lib/indicatorTimeSeries.ts` the single source of truth for both
the live dashboard (`computeIndicators.ts` just reads the last index) and
the backtest engine (`runBacktest.ts` walks every index). A backtest result
and what the dashboard would have shown on that historical day are
*provably* the same computation, not two implementations that happen to
agree today and silently drift apart later.

This was tested directly, not assumed: for several historical dates deep in
BANKBEES' 20-year history, the full-history snapshot at that date was
compared against a from-scratch computation using *only* data truncated up
to that date. Every field matched exactly at every tested date — EMA, ATR%,
RS trend, RRG quadrant, Renko signal, accumulation score, all of it. That's
the property a real backtester needs and a lot of homegrown ones skip.

## Strategy Builder & Backtest methodology (Phase 3)

**No-code conditions**: each strategy is a list of conditions (field +
operator + value + weight) drawn from `src/lib/backtest/fields.ts` — RRG
quadrant, RS trend/RoC/rank, Renko signal/trend age/reversal, trend
direction/strength, volume signal/spike/expansion, delivery trend/
accumulation score, and the composite score/signal itself. "Weighting
configurable" from the brief is implemented literally: a strategy's match
score on any given day is the weighted %% of its conditions that are true,
and `entryThreshold` is how high that %% has to be to trigger an entry —
100% reproduces strict AND, lower thresholds allow partial matches.

**Execution**: a signal evaluated using day *t*'s data executes at day
*t+1*'s Open (never the same bar's close that generated it — the standard
way to avoid feeding a strategy information it couldn't have had yet).
Exits are purely holding-period based (no early exit on a reversed signal,
by design — keeps "Holding Period Analysis" a clean, isolated variable).
Costs and slippage are applied as an adverse price adjustment at both ends.

**Position sizing**: a fixed allocation per trade (`positionSizePct` of
*starting* capital, not the current equity) rather than full compounding
reinvestment across simultaneously open positions — a deliberate Phase 3
simplification flagged in `runBacktest.ts`. Trade-level stats (win rate,
profit factor, average return, holding days) are unaffected either way
since they come from each trade's own return %. The equity curve and max
drawdown ARE affected by this choice — they're mark-to-market day-by-day
(realized P&L from closed trades + unrealized P&L on open ones), which is
real, but assumes a non-compounding capital base.

**Strategies are session-only** (consistent with the no-storage decision
from Phase 1) — export to a JSON file from the Strategies panel if you want
to keep one, and import it back in a later session.

## RRG methodology (Phase 2)

This reproduces the *publicly documented mechanics* of a Relative Rotation
Graph — relative price → light smoothing → rolling z-score ("RS-Ratio",
window 63 sessions) → a second rolling z-score of that ("RS-Momentum",
window 21 sessions), both centered on 100. It is **not** the exact
proprietary JdK RRG formula (that calculation has never been published) —
it's a transparent, from-scratch approximation tuned to produce the same
quadrant behavior, documented in `src/lib/indicators/rrg.ts`.

Quadrants: **Leading** (ratio≥100, momentum≥100), **Improving** (ratio<100,
momentum≥100), **Weakening** (ratio≥100, momentum<100), **Lagging**
(ratio<100, momentum<100). Rotation velocity/angle come from the day-over-day
vector in (ratio, momentum) space; transition compares today's quadrant to 5
sessions back.

## Renko methodology (Phase 2)

Classic close-based brick construction with the standard 2-brick reversal
rule. Brick size for the ATR method is **adaptive but strictly causal**: at
each bar, the next brick is sized using the ATR known as of that bar only
(never future data), so a symbol's brick size grows with its price/volatility
over a 20-year history instead of staying frozen at decade-old levels.
Once a brick is confirmed it is never revisited — appending new days only
ever adds bricks, it never rewrites history. See the comment above
`computeRenko` in `src/lib/indicators/renko.ts` for the full reasoning.

## Ranking methodology (Phase 2 — full spec weights)

Now that RRG and Renko both exist, ranking uses the exact weights from the
project brief: **RRG 25 / Relative Strength 25 / Renko 15 / Volume 10 /
Delivery 15 / Trend 10**. Composite signal: **BUY** ≥ 65, **WATCH** 40–64,
**AVOID** < 40. Every score comes from `src/lib/ranking/compositeRanking.ts`
with its reasons attached — nothing is shown unexplained, and the formal
Explainability Engine (`src/lib/explainability/explain.ts`) turns that into
the Signal/Confidence/✓✗-checklist format on the ETF Detail page. These
weights and thresholds are a starting hypothesis, not a tuned model — the
Strategy Builder/Backtester is exactly the tool to test that hypothesis
against real trade outcomes.

## Bundle size note

Plotly (RRG chart) and the backtest engine (Strategy Builder) are the two
heavier parts of this app. Both are lazy-loaded via `React.lazy`, same as
the ETF Detail page — none of them are in the initial bundle. Market
Overview, the default route, stays under 100KB gzipped; Plotly's ~360KB
gzipped chunk and the ~6KB Strategy Builder chunk only download when
someone actually opens those pages.

## What's intentionally not here yet

Multi-symbol Relative Performance comparison page, watchlists, weight-
editing UI on the dashboard itself, signal-based (non-holding-period)
exits, compounding portfolio simulation across concurrent positions, and
(per the Phase 4 decisions) the daily fetch running on an actual schedule
and the AI assistant having been tested against live NSE / live Anthropic
calls from this environment — both are built and ready, but need a real
run in your own GitHub repo and your own API key to confirm end to end,
which this sandbox's network restrictions don't allow.
